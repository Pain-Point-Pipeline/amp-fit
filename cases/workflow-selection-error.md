# Selection error in the first repository work pass

Recorded 2026-09-17 after Daniel corrected this pass. This is an unresolved
workflow failure and corrective record, not a claim that the method now works.

## The work that was already in front of the agent

Daniel and the agents have repeatedly tried to make Amp Fit derive useful Amp
work from evidence of a continuing responsibility. The discussion documents
repeated substitutions: category discovery, a supplied workflow brief, a comparer
program, a prescribed Thursday note, and then an attempted return to real work.
Daniel reports five changes of approach without resolving the central problem.
That count is his account; the repo and conversation provide the individual
artifacts and corrections, not a measured five-trial evaluation.

The current request was to use this repository and do the work as the Amp agent.
The strongest source was therefore the unresolved product/method work we were
already discussing, including this conversation and the repository's successive
designs. It did not need to be converted into a smaller technical defect to count
as recurring work.

## What the agent selected instead

The agent investigated native run records and open CI failures, then started
repairing evidence-ID instructions, revision metadata, and ROI refusal scoring
on an unmerged branch. These were real engineering issues. They were not the
central unfinished responsibility Daniel had just supplied.

The selection favored explicit error logs, bounded code changes, and readily
available pass/fail tests. It treated the repeated product corrections in the
conversation as framing for a different task rather than as primary work
evidence. It also inferred priority from what could be verified most easily.
Selecting an implementation-oriented execution skill before establishing the
responsibility reinforced that narrowing; the skill did not require choosing
these defects, and the agent remained responsible for the selection.
No instruction required that choice. The earlier recommendation to find a
different repository was the agent's proposal, and Daniel had explicitly
overridden it by directing the agent to use this one.

This repeated the product's failure: the measurement-friendly representation
selected the work, instead of the actual unfinished work selecting the approach.
Subagents and additional checks made the side work more thorough; they did not
make it the right work.

## Correction for this pass and future passes

Start from the unresolved responsibility expressed by the owner and supported by
the whole trail: conversation, design changes, implementation, reviews, and run
outcomes. A machine-readable log is not inherently stronger evidence of what
matters than an explicit unresolved owner correction.

For this pass, the responsibility is to diagnose and correct why Amp Fit keeps
substituting a predefined, easily graded task for the recurring work, and carry
that correction into the active design and operating path. A successful result
must address that mismatch. Runner fixes and an unrelated green PR cannot be
counted as completion.

State the chosen responsibility and cite the evidence before building. Compare
it with the owner's latest unresolved request. Use verification to judge the
work selected on that basis; do not use convenient verification to select a
different job. These are checks within normal engineering judgment, not a new
approval, scoring service, phase engine, or restriction to a fixed list of tasks.

The side repairs are parked separately with their actual verification status.
They may have independent value, but they are not proof of this task or a reason
to delay its correction. Historical native results and product capability flags
remain unchanged.

## Recognizing the work: what was missed and how to test a correction

Added 2026-09-17 after Daniel asked whether an agent can perceive work this way,
what else the same mistake hides, and how to approach future work systematically.

An agent can form a responsibility-level interpretation from a work history.
This conversation demonstrates recognition after the owner's correction.
Reliable recognition without that intervention remains unproven. The explanation
below concerns observable choices; it is not a measured account of the model's
internal reasoning.

### The evidence was available but given the wrong role

The agent treated the conversation as background explaining the project, while
treating failures in logs and tests as actionable work. That excluded the largest
unresolved responsibility before comparing possible jobs. Easy verification then
favored smaller defects, and delegation deepened that choice.

The lab contains the same narrowing explicitly: `d1/prompts.py` tells the agent
that the supplied packet is the workflow under study. It can evaluate execution
without discovering the important work. The current agent reproduced that
narrowing even though Daniel had authorized this repository as the case.

The continuing responsibility was to get Amp Fit to preserve the intended
outcome through discovery, design, execution, and evaluation. The manifestations
changed—category scans, comparers, notes, runner repairs—but the unresolved
outcome connected them. Repetition need not mean identical actions or files.

### Other work this selection rule hides

| Evidence present in this case | Work or burden it reveals |
| --- | --- |
| Daniel repeatedly explains the same distinction | Requirements interpretation and correction of the agent's understanding |
| Redesigns produce artifacts while the central question remains unanswered | Diagnosing why implementation progress is disconnected from the intended outcome |
| Earlier agent proposals persist after the owner redirects the work | Reconciling current decisions with inherited assumptions |
| Agents already perform work, but Daniel keeps rescuing their direction | Supervision and correction work that existing automation has not covered |
| Tests validate produced artifacts | Important omitted work can remain invisible to evaluation |

These are supported concerns in this case, not an exhaustive inventory. A repo
also cannot establish work that was never captured in any accessible source;
source gaps should remain visible rather than becoming invented opportunities.

Repeated attempts at one persistent failure do not necessarily establish a job
to schedule indefinitely. They may reveal a defect that should be eliminated.
The evidence establishes recurring effort; choosing among a durable repair,
continuing agent work, human judgment, or a combination requires further reasoning.

### A systematic approach without prescribing the job

1. **Recover the outcome that keeps bringing someone back.** Reconstruct relevant
   attempts: what was wanted, what was done, what happened, and what someone still
   had to do. Include corrections, abandoned approaches, and decisions alongside
   commits and runs. Keep source links so a summary cannot silently replace them.
2. **Infer the responsibility before choosing an intervention.** Challenge it:
   if the proposed work is completed, what substantial part of the owner's
   unresolved problem remains untouched? Apply this to the actual evidence,
   without generating a category inventory of speculative improvements.
3. **Choose what reduces the remaining burden.** A script may eliminate a stable
   operation; an agent may handle changing diagnosis and repairs; a person may
   retain priorities or consequential decisions. Existing automation covers only
   the work it actually handles. Do not preserve toil to justify future agent runs.
4. **Check what changed for the person doing the job.** Assess completed work,
   important omissions, and remaining effort. Distinguish useful human judgment
   from avoidable rescue, such as repeating an already settled objective. On a
   later occurrence, reassess demand rather than replaying the previous task list.

These questions can be applied within the existing case record and ordinary
agent work. They do not require a new controller or a document for every answer.

### What would establish improvement

Selection and execution need separate assessment. A relevant diagnosis can still
fail to produce useful work; a polished patch can still address the wrong job.
Record missed responsibilities, invented work, useful results, and human
correction effort. Without a measured human baseline, do not claim net time saved.

A replay of this known case can check for regression. It cannot show that a
method developed from this case generalizes to unseen work. That requires another
actual occurrence or responsibility whose answer has not already been taught to
the subject. Include resolved work and insufficient evidence when those states
occur naturally; do not plant them to force a preferred answer.

The [subagent test plan](plans/2026-09-17-2036-work-recognition-subagent-plan.md)
defines an immediate experiment using this repo, the visibility limits of the
shared environment, and the observations needed before making a stronger claim.
The explanation and plan are hypotheses about a repair, not experiment results.

The pilot has now stopped after two guided work passes. Its
[results and limits](cases/work-recognition-pilot-2026-09-17.md) are recorded
separately; they do not establish reliable recognition.

## Formulating work and its connections

Added after Daniel halted the pilot and asked how the system will understand
what work means, the roots of problems, and how the work interconnects.

### What exists and what is missing

METHOD.md currently asks an agent to recover the outcome, examine the trail,
infer a continuing responsibility, choose an intervention and check the result.
Those are useful requirements. They leave much of the relationship reasoning
implicit. Neither a coherent explanation nor two guided executions establishes
that the agent will consistently recover the right relationships.

For this method, a useful proposed unit of work is **a responsibility to close
or manage an evidenced gap between a needed outcome and the present state**.
The gap may be a failure, unmet request, investigation, coordination need or
continuing service obligation. It need not be a bug or repeat identical steps.
The repository supplies evidence and mechanisms; work can also involve decisions
and activity outside it. Missing outside context stays missing.

### Minimum representation

Keep the following distinctions in the existing case record. A table and source
links are enough initially; no database, fixed task taxonomy or extra agents are
required. These describe the reasoning, not a sequence of approval gates.

| Element | What it lets us answer |
| --- | --- |
| Outcome and beneficiary | Who needs what to become true, and which current instruction or accepted decision establishes it? |
| Present gap | What is happening instead, with evidence of its consequences or remaining human effort? |
| Attempts over time | What was tried, in which state, what happened, and what remained? Preserve abandoned approaches and successful fixes as well as failures. |
| Mechanisms and dependencies | What behavior produces the observation? What does the affected path depend on? Which relationship is merely suspected? |
| Continuing responsibility and current scope | What obligation connects the episodes, and which actions are justified now? Distinguish repeated repair of one defect from genuinely recurring new demand. |
| Intervention, ownership and outcome check | What could change the gap, what belongs to a person, and what observation would establish improvement? |

A work item can serve several outcomes and depend on several systems. Avoid
forcing the map into one folder hierarchy or a single root cause. Keep technical
dependencies, organizational ownership and causal explanations distinct.

### Relationships need evidence of their own

"Related" is insufficient. State whether one item **contributes to an outcome,
causes a symptom, blocks another action, implements a decision, tests a claim,
or supersedes an earlier attempt**. Record the source and applicable revision or
time; mark the relationship observed, inferred or unknown. An agent proposal is
not an accepted decision merely because it appears repeatedly in the history.

Shared files, similar wording, nearby dates and repeated commits are leads, not
proof of shared cause. Serving the same outcome does not imply the same cause.
A green check supports only what that check exercised. Contradictory evidence
must remain visible instead of being summarized away.

For a material causal claim, identify the behavior that connects cause to effect,
consider a plausible competing explanation, and say what observation would
distinguish them. A small replay or code trace may suffice for a technical claim;
an owner judgment may be necessary for usefulness. Until then, call it a
hypothesis. No experiment in this pilot reveals the agent's internal reasoning.

### A first map of the actual Amp Fit problem

| Connection | Evidence and status | Consequence for choosing work |
| --- | --- | --- |
| Owner outcome → evidence should determine Amp's job | Explicit repeated owner requests, preserved in this conversation and the case record | The outcome is broader than producing a predetermined artifact. |
| Supplied miniature workflow → discovery already decided before execution | Baseline packets and D1 prompt prescribe the work; observed implementation | Improving execution inside that packet cannot establish work discovery. |
| Exported comparer → host success on that comparer | Baseline D1 evaluator executes the export against expected outputs; observed implementation | This checks a specific component. The link from that success to useful recurring work is unsupported. |
| Changing comparer to prescribed note → same selection problem survives | Both proposals name the job before examining a real trail; supported interpretation of the supplied discussion | Changing the output format alone does not address the demonstrated mismatch. |
| Available test failures → agent selects adjacent repairs → owner redirects it | Actual first pass and Daniel's correction; the sequence is observed | The repairs were real work, but their completion would leave the selected owner outcome unresolved. Preference for easy verification is an explanation of the observable selection pattern, not a measured internal cause. |
| Outcome remains unresolved → Daniel repeatedly restates it | Owner corrections are observed; their duration/cost is unmeasured | Count correction as remaining work. Do not treat existing agent activity as coverage of the whole responsibility. |
| Active instruction repair → fewer future substitutions | Proposed causal relationship; unproven | The document change is delivered. Reliable future selection is still a separate claim. |

This map exposes a broken connection between the outcome sought and the success
being measured. It also leaves room for other causes: stale inherited guidance,
missing context, execution defects and product judgment need their own evidence.
"The agent was lazy" does not identify an observable mechanism to repair.

The v3 pass illustrates a different relationship. Citation rejection, misleading
empty-state presentation and false selection receipts affected the same
discovery-to-selection outcome. They had separate mechanisms. The citation replay
supports one local causal explanation; it does not explain the entire product's
work-selection problem or prove that the restored proposals were useful.

### How this changes the next ordinary work pass

Start with the current unresolved request and reconstruct the smallest connected
account that explains it. Follow evidence both toward the intended outcome and
through the dependencies that produce the current behavior. Expand beyond a
file or subsystem when a material connection requires it. Record disconnected
findings as separate work; do not silently let them replace the assignment.

Before choosing a fix, ask what would remain wrong if it succeeded. Before
closing the work, check the actual gap and remaining human burden. On the next
occurrence, update the changed facts, superseded decisions and residual demand;
do not repeat completed work simply because it appears in the history.

Scope is sufficient for a decision when the supported account explains the
chosen intervention and material known alternatives, dependencies and omissions
are explicit. This is a provisional boundary, not a claim to know everything
in the repo. Expand it when new evidence could change the decision. A missing
human decision blocks only the actions depending on that decision.

Reliability would mean these connections survive challenge and later outcomes:
the sources support them, contrary evidence changes them, and successful local
actions translate into progress on the stated outcome. We have not established
that reliability. The next design object is this inspectable account of work
and relationships, beginning with the map above; no further agent trial or new
execution framework has been started.
